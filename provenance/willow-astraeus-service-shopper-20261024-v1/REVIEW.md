## Collector and same-turn confirmation

The existing `heal_ally` live loop still applies its original self/spawn/team/kept-recall exclusions, current gain/health-fraction threshold and strict target comparison. It copies deficit, fraction and trip weight for every eligible record before threshold rejection, in existing native scan order. No second recipient scan or new live-unit/inventory/round import is added. Storage is fixed: eight cast snapshots, at most 16 scalar recipient entries each (matching World's side-index bound), one staged cast, pending/published profiles, counters and scalar provider state.

Trip weight uses the existing recipient maxHP read, the already-kept recall length, and the ready cached own-spawn field at the recipient's scanned tile. Fast-recall data must have been observed in the current round (`stats_round`); a newly revealed recipient with older item knowledge makes that whole snapshot uncovered. A missing/unreachable/not-ready route, invalid maxHP, native-read failure or buffer overflow also marks the entire snapshot excluded. Failed route-table lookup is caught separately so it cannot skip an otherwise usable ordinary heal target. Excluded successful casts still occupy a slot in the last-eight ring and keep their time in exposure; no alternate target is invented by dropping an unknown record.

Only an actual successful ordinary cast stages a scan. Scan round/observation identity and item epoch are recorded without an additional import. `play_turn` reuses its existing `!world.is_stale()` call and confirms the staged cast only at that boundary. Rollover, observation mismatch and changed item epoch yield no measured service. If StaleTurn abandons the function before confirmation, the next observed turn discards/counts the outstanding event. Planner `Op::heal` successes are staged/counted as uncovered at the same boundary; their older target records never enter the service estimate. Failed casts add no sample. Coverage counters distinguish verified ordinary casts, covered casts, missing-data casts, planner successes and unknown successful events.

## Exposure, epochs and publication

Alive-turn ordinals come directly from existing `Upkeep.turns`. Before eviction, exposure begins at the collecting inventory/stat epoch's first alive turn. After the ninth and subsequent successful ordinary casts, the start advances to immediately after the evicted cast's ordinal. Exposure ends at shop publication; long alive periods without service dilute the estimate. Ordinary observed dead turns neither add alive exposure nor create a gap. An unknown round gap or unconfirmed prior turn clears/rebases pending history and ends the known continuous visit.

Provider Strength/Focus/maxHP changes are compared using the existing play-turn self record. Every successful shard purchase clears pending history and advances its stat/emblem epoch, using existing `bought` arithmetic to update expected provider stats. Consumables do not reset it. Pending invalidation never clears the current visit's published observations.

At the start of an observed dead/on-spawn visit, before any chooser can run, pending history is copied to one published profile and revision increments. Spawn membership uses the already-stored spawn positions and already-read self position, with no extra native tile query. Publication remains fixed across subsequent dead/spawn turns, including respawn and multiple purchases; an observed live off-spawn turn ends the visit. No profile is republished after each heal or each buy-loop iteration.

## Shared signed utility and exact shopping scope

`BuildUtility::saved(b)` is the one implementation of `own_upkeep(now) - own_upkeep(b) + observed_service(b) - observed_service(now)`. It retains all original own Strength/Health/clear-speed/damage/recovery terms. The service evaluator applies the original `worth_healing`, maximizes clipped HP gain, then uses the original fraction/order tie rules over every retained known scan. It multiplies the selected target's accepted HP by that target's recorded fractional recovery-trip weight and divides by the same published alive exposure. It can select a different target or none, and its difference remains signed. No replacement reset or unobserved future cast is credited.

Full completion in `best_emblem` and actual affordable partial/completion Builds in `affordable_prefix` use that same utility. Original `add_shards`, `add_completion`, family passives, remaining counts and gold costs stay authoritative. `prices` retains the chosen full saving/cost through its original conversion, adding an explicit published-profile revision to the original cache key. Service results are cached for up to 16 distinct Focus values within each quote evaluation; overflow would simply compute the scalar value without caching, not change gameplay admission.

Before Treasure ownership, service is bypassed, fresh Bruiser Focus is absent, the original strict candidate order remains, and `Treasure.stat = best.stat`/begun Treasure arithmetic are unchanged. The new Prices key component remains zero there. After Treasure, fresh Bruiser Focus is appended after the existing candidates using the same strict greater-than rule; it does not displace an exact tie. All original begun-item early returns stay in place. Existing inventory reads supply the cached Treasure-owned flag; known Treasure completion updates it without an added item read. During a same-visit loop, the frozen observations remain while `bought` and actual partial/completion effects change the Build being priced.

Source algebra controls (not executed tests): cap300/360 at deficit190 and fraction≥0.5 yields190/0 accepted HP, a negative service difference. Below0.5 it yields190/190. Different recorded recipients can change the selected target when the acceptance floor changes; the selected recipient's own weight follows that target. Completed Willow Bruiser Strength/Focus compare today's cap+15 versus cap+75, with the existing 12-Strength opportunity cost and equal50HP retained in own upkeep. A Health Build with unchanged Focus adds no direct service value; a completion that adds Focus receives only that actual cap effect. Prefixes use their exact shard count, not a prorated completed-item score.

## Diagnostic seam, cost and review boundary

All new output is inside the repository's existing opt-in `debug_block` seam; Release omits it. `SERVICE-PUBLISH` records revision, sample/known counts, alive exposure and lifetime coverage counters; `SERVICE-QUOTE` records full family/stat/cost, current/proposed cap, signed service term and total saving (capped256 diagnostic rows); `SERVICE-PREFIX` records actual affordable count/completion and matching terms (capped128); `SERVICE-BUY` records actual successful shard purchases. These rows use existing scalar values and add no live observations. Profile age can be related to the publication round/revision; they are estimates, not proof of an avoided recall or later productive work. Debug instrumentation has its own SDK/debug/printf overhead and cannot certify fuel-equivalent Release behavior.

The only added data-read host calls are bounded `sdk_DistanceField_Get` operations for already-scanned eligible recipients when the spawn field is already ready. No field construction, route search, communication or new live-world native read is added. Fixed-array copies, provider/visit bookkeeping, up to8×16 scalar recipient comparisons per distinct candidate Focus, and existing cache misses add fuel. There is no allocation or new fuel gate introduced by the profile/cap code; existing live-position vectors and other shopper work retain their original allocations. Before Treasure and for non-Willow actors the nominal choice/model is preserved, but no runtime fuel/action equivalence is claimed.

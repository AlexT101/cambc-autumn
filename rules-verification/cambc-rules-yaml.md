# Plan: build `cambc-rules.yaml`

## Goal

Write `cambc-rules.yaml` at the repo root: a concise, declarative source of truth for the rules of Cambridge Battlecode 2026a. Other AI agents will read it instead of the full docs.

**Concision is the main requirement.** Every line must carry a rule or value a bot author needs. Don't write explanations, motivation, examples, restated rules or filler, and don't spell out the obvious. Say each fact once, in the most general place it applies. When in doubt, cut it.

## Context

- **Language:** our bot is C++ only. Ignore the Rust, Python and OCaml SDKs, guides, API pages and LLM exports.
- **Sources** (read-only; never edit `docs/`, it is regenerated by `tools/docs-sync`):
  - `docs/handbook/*.md`: rules chapters. The `<details>` "Interactive diagram text" blocks hold rule detail missing from the prose (round phases, cooldown ticking, ward recharge, dash over altars, cast/walk rules). Read them.
  - `docs/champions/*.md`: the roster and the kit and stats for each champion.
  - `docs/guides/cpp/*.md`, `docs/api/cpp.md`: the C++ API, for building test bots. Don't copy them into the YAML.
  - `docs/llm/GameRules.md`: single-file rules export (the handbook prose without the diagram text). `docs/llm/BotAPICpp.md`: the API in one file.
  - `sdk/cpp/cambc.h`: the C++ SDK. At runtime it exposes engine values: `game_settings` (capture, sleep, respawn, recall and tribute timings, kill/assist/passive gold, spawn healing, ward cooldown/lifetime/radii, tile_reveal_rounds, altar_lock_hits, tp_crystal_time, …), item and consumable info, ability properties, champion and camp stats, and passive constants. Note `vec2::north == {0, 1}`.
  - `sdk/cpp/effect-tests/src/bot.cpp`, `sdk/cpp/tests/src/bot.cpp`: example SDK bots, useful as templates.
  - `unswbc-rules.yaml`: a reference file for a different game. Copy its style (terse declarative sentences, nested sections, exact numbers, explicit orderings and tie-breaks), not its content.
- **Tooling:** the `cambc` CLI is installed (`new`, `build`, `run`, `view`). The 9 competition maps are in `maps/`. They are binary, and the map editor is a GUI, so use the existing maps.

## Subagents

You may spawn subagents for any part of the work: reading sources, triaging, building probe bots, running matches, or drafting YAML sections. Run up to **8 at a time**. A good split for Phase 1 is one subagent per ambiguity (or per small group of related ones), each building and running its own probe bot in parallel.

To keep parallel runs from interfering, give each subagent:
- a unique bot name (`bots/probe-<topic>`);
- its own output directory (`-o <scratch>/<topic>`);
- a precise question, plus the exact evidence to report back (log lines and conclusion).

You own the final conclusions and the YAML. Check what subagents return before relying on it.

## Phase 1: find and settle ambiguities (do this first)

### 1a. Triage

Trust the docs wherever they give a clear answer. Read all the sources and list only rules that are **genuinely unclear**: sources contradict each other, a quantity or ordering is missing, or a timing or edge case would change bot behaviour.

A general rule with a stated exception is clear, not ambiguous. For example, "all monsters have range 3" alongside a table giving the Monolith range 5 needs no test. Where sources differ in detail, prefer the more specific one (table > diagram text > prose summary).

Seed candidates (re-triage these yourself; drop the clear ones, add any you find):

1. **Ward timing.** The docs say "relocate every turn", "replace once per round", "Recharges after 1 round" and "trinket charge". Settle the real cooldown and lifetime, whether ward vision is shadowcast from the ward tile, and which tiles can hold a ward.
2. **Camp sleep.** "Does not take damage for 2 turns" vs "two rounds without an in-range champion". Also how a camp picks its target and breaks ties.
3. **Capture timer.** How many rounds from first uncontested occupancy to reward.
4. **Ability cooldown.** On which of the caster's turns can a slot cast on turn t be cast again?
5. **Ranged allowance.** Does attack-reset restore only the attack, or the walk too? Does walk-then-attack vs attack-then-walk matter?
6. **Stun.** How many of the target's turns does a "one-round stun" remove, given that teams alternate who starts each round?
7. **Teleport crystal.** "Can reach walls" vs "cannot land on a wall". Settle the landing rules.
8. **Gold modifiers.** Do Treasure/Vesper bonuses apply to kill and capture gold? How does gold round? What are `passive_gold` and `assist_gold`?
9. **Shared memory.** Is a write visible to a teammate who acts later in the same round?
10. **Fuel exhaustion.** Is the suspended turn simply lost? Is the draft's 10x budget for the first pick turn only?
11. **Out-of-vision handles.** Which fields of an unseen ally or enemy champion can be read? What does `tile_reveal_rounds` control?
12. **Coordinates.** Origin, axis directions, and how each symmetry type maps tiles.
13. **Turn order.** Priority ties, Cassi/Issac ordering, and where dead champions' turns fall.

### 1b. Test against the engine

Settle every unclear item by testing. Use the cheapest method that works:

1. **SDK introspection.** One probe bot prints, on its first turn: every `game_settings` field, item and consumable info, each champion's ability properties and base stats, camp stats, map size and symmetry, and terrain coordinates. Many items are settled by this dump alone.
2. **Deterministic scenario bots.** Create one with `cambc new probe-<topic> --lang cpp`. Give it a fixed draft and scripted actions so the game reaches the situation under test on a known map, then run `cambc run probe-a probe-b --map <name> --rounds <N> -o <dir>`. Team A is the first bot. Use two different bots when you need a passive opponent.
   - Log one line per observation, `PROBE <round> <champion> <key>=<value> …`, with every value read from the engine, never from your own counters.
   - The output `.repl26a` file is a zip containing `team-a.stdout` and `team-b.stdout`. Bot output appears there in order, mixed with binary markers: strip non-printable bytes and grep for `PROBE`. Engine errors are logged there too.
   - The game is deterministic, so a rerun should reproduce the same logs.

If a first attempt doesn't reach the scenario, change the approach: a different map, opponent script or champion. Keep going until each item has an answer.

Record each item in `rules-verification/findings.md`: question, method (bot, map, rounds), key evidence, and conclusion, a few lines each. Keep the probe bots in `bots/probe-*` so results can be reproduced.

## Phase 2: write the YAML

- **Declarative facts only.** No metadata, versions, dates, history, sources, caveats or verification notes.
- **No API listings.** Use game terms. Mention an SDK name only where it differs from the rules term and the mapping matters.
- **Coverage:** objective and result, map and coordinates, draft, round and turn order, action allowances, movement, combat, abilities and effects, channels, camps and capture, gems and altars, economy, vision and wards, death, recall and respawn, memory, fuel, and champions.
- **Values:** every number comes from the docs, the settings dump or a test. Where a test contradicts the docs, write the tested behaviour.
- **Shape:** mirror the reference: top-level sections, short keys, one-sentence values, `sequence:` lists for ordered phases, flow mappings for tables. State shared defaults (vision 8, cooldown 8, one cast per turn) once, not per champion. For example:

```yaml
camps:
  types:
    wolf: {health: 1350, strength: 20, range: 3, gold: 90, gems: 22, respawn: 40}
champions:
  ryth:
    attack: melee
    stats: {health: [1200, 100], strength: [50, 5], focus: [100, 10]}  # [base, per shard]
    passive: "Gains Strength equal to 1% of bonus health."
    abilities:
      - {name: area_stun, effect: "1x Focus damage and a one-round stun in radius 1.", target: ground, range: 4, walking: excluded}
```

Aim for about 250 lines or fewer. Shorter is better if nothing is lost.

## Phase 3: review

- Every number and rule traces to `docs/` or `rules-verification/findings.md`.
- Cut anything duplicated, implied by another line, or not needed to play. Make one tightening pass purely for length.
- Nothing from the non-C++ tracks, no API lists, no metadata. The file parses as YAML.
- Fresh-agent test: could someone write a correct bot from this file plus `docs/api/cpp.md` alone?

## Deliverables

1. `cambc-rules.yaml` at the repo root.
2. `rules-verification/findings.md` and the `bots/probe-*` bots behind it.
3. A brief summary for the user: what was tested, and which test results contradicted the docs.
